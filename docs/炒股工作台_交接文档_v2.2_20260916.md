## 3. 系统怎么跑

### 3.1 架构（混合：静态骨架 + 前端实时补丁）

```
GitHub Actions（免费定时执行，无运维）
  13:40 预热   → 抓 120 个板块日K线 / 解禁 / 减持 / 新闻 / 宏观 / 财经日历（不依赖收盘）
  14:00 主评分 → 抓盘中快照 → 12 维 → 写 JSON（含大盘关键位、事件日历）→ 提交 → 重新部署 Pages
  15:30 收盘复核 → 用收盘价重算并归档
        ↓ 产物（web/data/**）
GitHub Pages（静态托管，发布的是 CI 上传的 web/ 快照）
        ↓ 手机/桌面打开
纯前端 PWA：读 JSON 秒开 → 1 次 JSONP 补实时 → 本地微调分数 → 刷新 UI
```

**为什么必须混合**：14:00 属盘中，Actions cron 有 5–30 分钟延迟，不能作为盘中决策的唯一时间源；
前端实时补丁保证「此刻打开看到的就是此刻的市场」。

**⚠️ 关键认知**：Pages 发布的是 **CI 上传的 `web/` 快照，不是分支内容**。
改了 `web/` 下的静态文件后，**必须重跑一次 workflow** 才会生效（只推 git 不重跑 = 线上不变）。

### 3.2 每日时序与触发方式

| 时点（北京） | 阶段 | cron (UTC) |
|---|---|---|
| 13:40 | `warmup` 预热 | `40 5 * * 1-5` |
| **14:00** | `score` 主评分 | `0 6 * * 1-5` |
| 15:30 | `close` 收盘复核 | `30 7 * * 1-5` |

手动触发（**不需要点网页**）：
```bash
POST /repos/chuanwudi46-ops/Big-A/actions/workflows/daily.yml/dispatches
body: {"ref":"main","inputs":{"stage":"warmup|score|close"}}
```

**⚠️ 换宇宙或大改后必须「先 warmup 再 score」**：K 线缓存 key 带 `run_id`，
`restore-keys: kline-` 只恢复最近的。换宇宙后旧缓存里没有新板块，
`stage_score` 对无缓存板块会 `[skip]`（结果 count 不足）。只跑 score 会缺板块。

## 4. 数据通道：实测事实（本项目最值钱的一节）

### 4.1 东财各域名在海外 runner 的真实可达性（探针实测，非猜测）

| 端点 | 海外 runner | 国内本机 |
|---|---|---|
| `push2.eastmoney.com`（clist/kline） | ❌ 302→502 | ❌ 不可达 |
| `push2his.eastmoney.com`（kline） | ⚠️ 连几次后断连（000） | ❌ 断连 |
| `push2delay.eastmoney.com` **clist** | ✅ 稳定 | ✅ 稳定 |
| `push2delay.eastmoney.com` **kline** | ⚠️ **软限流**：HTTP 200 但 `klines=[]`、`dktotal=0` | ⚠️ 同左 |
| `datacenter-web.eastmoney.com` | ✅ 200 | ✅ 200 |
| 腾讯行情 / 新浪行情 | ✅ 200 | ✅ 200 |

**结论：东财 K 线通道在海外 runner 上彻底不可用，必须换腾讯。**

### 4.2 当前各用途的取数优先级

| 用途 | 优先级 | 备注 |
|---|---|---|
| 板块日 K 线 | **腾讯 → 东财直连 → akshare** | 腾讯唯一可用接口见下 |
| 板块快照 / 成分股 | **东财 `push2delay` clist 直连** | 含 `f62` 主力净流入、`f3` 涨跌幅 |
| 高管持股变动 | **`datacenter-web` + 服务端 filter** | 0.98 s（akshare 同数据要 8 分 49 秒） |
| 前端实时补丁 | 浏览器直连 `push2` → `push2delay` 兜底 | **顺序不能反**（见 4.4） |

### 4.3 腾讯 K 线通道（唯一可用）

```
# 只有这个接口能用（对一级/二级/三级板块都有效）
https://proxy.finance.qq.com/ifzqgtimg/appstock/app/newfqkline/get
    ?param={code},day,{start},{end},{count},qfq

# 代码规则：pt01 + 申万 6 位码
#   一级 电子     = pt01801080
#   二级 种植业   = pt01801012
#   ❌ 不要用 web.ifzq.gtimg.cn/appstock/app/fqkline/get —— 对板块只返回 1 根 bar
```

- **榜单接口只列一级 31 个**：`proxy.finance.qq.com/cgi/cgi-bin/rank/pt/getRank?board_type=hy`
  —— 它只是「发现代码」的入口，**取数要自己用申万码拼**。
  曾误判为「腾讯只支持一级」，实际是榜单的视角限制。
- bar 字段：`[日期, 开, 收, 高, 低, 成交量(手), {}, 换手率%, 成交额(万元), ...]`
  - 成交额 **×1e4** 换成「元」以对齐东财口径
  - **涨跌幅一律用收盘价 `pct_change()` 自算**，不要按 bar 下标取（不同品种长度不一）
  - 取数区间**向前多留 15 天再裁剪**，否则增量更新的首根 bar 涨跌幅为 0
- 实测：**120/120 成功、6.8 s**

### 4.4 东财接口的硬坑（都已踩过，代码里留了注释）

1. **clist 单页 `pz` 被服务端硬截断到 100**：分页终止条件必须拿「服务端实际返回页大小」比，
   不能拿请求的 `pz` 比。否则 496 个板块只取到 100 个。
   - **后端**：板块清单/成分股被静默截断
   - **前端更隐蔽**：`fs=m:90+t:2` 默认按涨幅降序，一次请求 `pz=600` 只回前 100 名 ——
     关心的 31 个板块**只有 2 个命中**，其余 29 个的实时标记与三项微调**静默失效、页面无报错**。
     现按 `data.total` 并发翻满 5 页（`LIVE_PAGE=100`），实测命中 120/120。
2. **分页排序键必须用静态字段 `f12`（代码）+ `po=0`，绝不能用 `f3`（涨幅）**：
   涨幅盘中一直在变，翻页那几百毫秒内列表重排会让跨页边界串位。
   实测 `fid=f3&po=1` 拉 496 个板块会**重复 1 条、漏 1 个**；换 `fid=f12&po=0` 后 496=496 零重复。
   这是历史上「随机掉块」的另一来源（与 K 线通道抖动**是两回事**）。
3. **`datacenter-web` 的 `sortTypes` 个数必须与 `sortColumns` 完全一致**，否则
   HTTP 仍是 200 但 `result: null` + `message: 排序字段和顺序数量不一致`。
   已改为按列数自动生成，且 `result is None` 时**把 message 抛出来**（不抛就无从排查）。
4. **`secids=90.BK1201,...` 在 clist 上不可用**（返回 `rc:102` / `data:null`），
   只能全量拉后本地按 code 建索引。`fs=b:BK1201` 的语义是「该板块的**成分股**」，不是板块自身。

### 4.5 无源标的必须与网络抖动区分开（120 个板块下构建不超时的关键）

| 现象 | 判定 | 处置 |
|---|---|---|
| 每次挂的**是不同标的** | 限流 / 抖动 | 退避重试 + 换源 |
| 固定挂**同一端点** | 地区封锁 | 只能换源 |
| 固定挂**同一批标的** | **无源**，不是抖动 | **立即放弃，不要重试** |

已定义 `NoHistorySource` 异常：空结果或长度不足时抛出 → 业务层**不重试**、返回空 DataFrame、
计入独立计数器 `nosrc`。若给无源标的也配「3 次重试 + 超时」，十几个无源标的
就能凭空多出十几分钟。日志格式 `ok/skip/fail/nosrc` 分开计数，一眼能分辨。

### 4.6 财经日历（事件日历的数据源，v2.1 新增）

**结论：东财 `datacenter-web` 有现成的「财经日历」报表，是真实事件表，可直接用。**

```
报表名：RPT_CPH_FECALENDAR
        https://datacenter-web.eastmoney.com/api/data/v1/get
          ?reportName=RPT_CPH_FECALENDAR&columns=ALL
          &filter=(START_DATE>='2026-09-16')(START_DATE<='2027-01-14')
          &sortColumns=START_DATE,FE_CODE&sortTypes=-1,1
          &pageNumber=1&pageSize=500&source=WEB&client=WEB
```

- **报表名不是猜的**：从 `https://data.eastmoney.com/cjrl/` 的页面 JS
  （`/newstatic/js/cjrl/default.js`）里 grep 出来的。报表名写错时接口会明确回
  `{"success":false,"message":"报表配置不存在,RPT_xxx"}` —— 所以「有没有这个报表」是可判定的，
  不要凭记忆写接口名。
- **实测覆盖**（2026-09-16 ~ 2027-03-31 共 1476 条）：
  美国 CPI / 非农 / 核心 PCE / ISM / GDP / 零售 / PPI / 初请失业金、中国 LPR / CPI·PPI /
  PMI / GDP / 进出口 / 社融·M2 / MLF 到期、各国央行议息会议（美联储 / 日本 / 英国 / 欧洲 /
  澳洲 / 瑞士 / 新西兰 / 加拿大）、行业与政策会议、新股申购。
- **字段**：`START_DATE`（带时刻，如 `2026-10-02 20:30:00`）/ `END_DATE` / `FE_CODE`（唯一）/
  `FE_NAME` / `FE_TYPE` / `CONTENT`（超长，**取数时已剔除**，见下）/ `CITY` / `SPONSOR_NAME`。
- **性能**：4 个月区间 1543 行、**1.29 s**（4 页 × pageSize 500）。
- **踩坑**：
  1. `sortColumns` 必须带唯一列：只按 `START_DATE` 排序时同一天有几百条，
     翻页边界会重复/漏条（与 clist 用 `f3` 排序掉块同一类问题）。用
     `START_DATE,FE_CODE` 排序 + `dedupe_on="FE_CODE"` 兜底。
  2. `sortTypes` 个数必须与 `sortColumns` 一致（4.4 已踩过，日历接口同样适用）。
  3. `CONTENT` 列是体积大户（单条几千字），事件日历用不到 → `econ_calendar()` 直接不取它，
     parquet 从约 1 MB 降到 **55.6 KB**，不会让仓库按天膨胀。
  4. 日历源**没有**「重要性」字段，也没有股指期货交割日与解禁 —— 这三块靠自建规则补：
     优先级规则表（`config/events_rules.json`）、第 3 个周五推算、`release.parquet` 解禁市值。

**事件日历的四路数据（每条事件都带 `src` 标明出处，不把推断伪装成官方）**

| src | 来源 | 说明 |
|---|---|---|
| `eastmoney` | 东财财经日历 | 真实事件表，主力 |
| `rule` | 规则推算 | 每月第 3 个周五 = 中金所股指期货/期权交割日 |
| `release` | warmup 产出的 `release.parquet` | 单日解禁市值 ≥150 亿成一条事件，≥450 亿升为高优先 |
| `curated` | `config/events_rules.json` 的 `curated` | 中央经济工作会议 / 政治局会议 / 两会等**惯例窗口**，前端标注「惯例」 |

**归类合并是必须的，不是可选优化**：原始日历里同一件事有多个口径
（美国非农 4~5 条、CPI 有同比/环比/核心），直接铺出来会被噪音淹没。
规则把原始条目映射到「规范事件」，再按 `(日期, 规则id)` 合并成一条，原始明细保留在
`detail` 里供展开。四个必须留意的匹配坑：

- **规则表的顺序即优先级，兜底规则必须排最后**（`us_other` / `cn_other` 这类会吃掉一切）。
- **港台数据必须先拦掉**：东财命名里 `中国香港:CPI` / `中国台湾:PPI` 都含「中国」二字，
  不先把它们单独归到 `hmt` 规则，就会被 `cn_cpi_ppi` 吃掉 —— 实测「中国 CPI/PPI」
  因此每周出现一次（4 个月 14 条 → 修正后 4 条）。
- **惯例清单的去重只能按关键词**，不能按「窗口内有没有别的中国事件」：
  按后者会把 12 月中旬的「中国月度经济数据」误判成已覆盖，从而把中央经济工作会议整条吞掉。
- **美联储议息会议与其新闻发布会相差一天**，同属一次会议 → 规则里给
  `merge_window_days: 1`，合并后取**较晚**那天（决议真正公布、市场反应的时刻）。

## 5. 板块宇宙：申万二级 120 个

### 5.1 是怎么定下来的

```
申万二级官方名单 131 个
   ∩ 东财行业板块清单  → 127 个（4 个东财无同名板块，见下）
   − K 线不可用标的 7 个 → 120 个（当前宇宙）
```

- 生成脚本：`pipeline/build_universe.py`；产物：`pipeline/config/board_universe.json`
- **4 个东财未匹配**：国有大型银行Ⅱ、股份制银行Ⅱ、城商行Ⅱ、农商行Ⅱ
  （东财未做同名板块或层级切分不同）
- **7 个被剔除**（`no_kline`）：林业Ⅱ、农业综合Ⅱ、其他家电Ⅱ、旅游零售Ⅱ、体育Ⅱ、油气开采Ⅱ、医疗美容
  - 6 个腾讯无此指数；1 个（**林业Ⅱ**）是僵尸指数 —— 数据冻结在 2021-12

### 5.2 「可用」的判定判据（两个条件都要，缺一会误判）

```python
usable = len(df) >= 250 and (today - df.index[-1].date()).days <= 45
#        ↑ 条数足够              ↑ 最后一根 bar 足够新
```
只看条数会把僵尸指数误判为可用；它接进宇宙后永远算不出当日动量，把整条链路拖脏。

### 5.3 为什么要保留「可切层级」的能力

`board_universe.json` 的 `level` 字段改一行即可换层级，但它同时带
`levels`（三级名单都有）、`board_codes`、`sw_codes`、`parents`。
**为什么不用东财 496 个**：东财已扩为三级细分共 496 个，且接口不返回层级字段，
无法干净分层。申万官方名单带「上级行业」字段，故以申万为准收敛。

**换宇宙后要跑**：`python pipeline/sync_boards.py --force` 重建元数据，
然后**先 warmup 再 score**（见 3.2）。

## 6. 评分体系（与 v1.0 规格一致，此处为代码实际值的校准版）

### 6.1 十二维权重（`pipeline/config/weights.yaml`，改配置不改代码）

| # | 维度 | 权重 | 计算要点 |
|---|---|---|---|
| 1 | 动量 | 10% | 5/20/60 日涨幅加权 + 相对沪深300 超额 |
| 2 | 趋势结构 | 10% | MA20/MA60 位置、多头排列、KDJ(9,3,3) |
| 3 | 量价健康 | 8% | 调整期缩量比、上涨放量比、量价背离 |
| 4 | 换手率位置 | 8% | 板块换手率 250 日分位。**✅ 2026-09-16 已修正方向**：`factors.turnover()` 现返回 `1 − _pctrank(turnover)`（**低换手加分**）。修正前是 `_pctrank(turnover)`（换手越高分越高），与配置注释、前端实时补丁、回测数据**三方都相反** —— 见 6.5.3 |
| 5 | 主力资金流 | 10% | 主力净流入占比 |
| 6 | 估值位置 | 10% | PE/PB 历史分位；**当前无真实行业 PE，用 252 日价格分位代理**（产物标 `valuation_source`）。**⚠️ docstring 沿用 PE 语义写「越低越好」，但价格分位下是「越高越好」——回测支持现行代码，该改的是注释**，见 6.5 |
| 7 | 周期位置 | 8% | 价格动量 + 涨价信号关键词 |
| 8 | 行业出清度 | 6% | 出清链条阶段（**人工维护静态表**） |
| 9 | 政策强度 | 6% | 反内卷 / 供给侧 / 稳增长关键词 |
| 10 | 新闻情绪 | 12% | 情绪分 × 时效衰减 × 板块相关度 |
| 11 | 板块共振 | 12% | 成分股涨跌一致性 + 龙头同步 |
| 12 | 筹码供给 | 罚分 0–20<br>**实际上限 4** | 未来 30 日解禁市值/流通市值 + 近期减持公告数。<br>**⚠️ 2026-09-16：解禁项已退出罚分**（`release_weight: 12.0 → 0.0`），只剩减持项（上限 4 分）。解禁占比/市值仍逐板块写在产物 `penalty_detail` 里作**提示**，不参与分数 —— 理由见 6.5.4 |

### 6.2 计算公式

```
f_i     = 因子按滚动 250 日窗口做分位归一化 → [0,1]
S_base  = 100 × Σ(w_i × f_i)                        # Σw = 1
P_supply = min(20, 12×解禁压力归一 + 4×减持久归一)
           ↑ 2026-09-16 起解禁项系数为 0 → 实际上 P_supply = min(20, 4×减持久归一)
命中负面清单 → 分数上限压至 45 并打「回避」
S       = clamp(S_base − P_supply − P_blacklist, 0, 100)
```

### 6.3 分级与动作

| 分数 | 标签 | 动作提示 |
|---|---|---|
| ≥75 | 主升共振 | 逢低吸：网格分批，单次 5% |
| 60–75 | 进入观察 | 小仓试探，跌破支撑才加 |
| 45–60 | 中性 | 卧倒 |
| 30–45 | 转弱 | 逢高减：分批累计 30% |
| <30 | 回避 | 空仓，等解禁出清后的「黄金坑」 |

### 6.4 宏观分 M 与决策矩阵（关键设计，勿改成「乘数」）

宏观四要素：**流动性 30 + 量价 25 + 政策 25 + 情绪 20**，
其中**情绪项做逆向映射**（对应帽子哥「散户情绪极差 ≈ 无关变量甚至反向指标」）。

| 板块分 S ↓ / 宏观分 M → | M≥70 进攻 | 40≤M<70 中性 | M<40 防守 |
|---|---|---|---|
| ≥75 | 按网格分批建仓 | 小仓试探（≤半仓） | 只观察不动手 |
| 60–75 | 观察，跌破支撑再加 | 观察 | 观察 |
| 30–45 | 逢高减 30% | 逢高减 | 逢高减（加速） |
| <30 | 回避 | 回避 | 回避 |

**设计意图**：板块分决定「买什么/卖什么」，宏观分决定「能用多少仓位」。

### 6.5 回测裁决：这套分数与规则，用真实历史数据检验的结果（v2.2 新增）

完整报告：**`docs/backtest_report_hist.md`**（387 行，含全部表格与偏差声明）。本节是摘要与**可执行结论**。

#### 6.5.0 怎么做的（以及为什么不能直接用 `backtest.py`）

| 项 | 说明 |
|---|---|
| 方法 | **点内（point-in-time）重建**：评价日 t 只把 `df[:t+1]` 喂给 `pipeline/factors.py` 的**原函数**，不重写公式 —— 否则「回测通过」与「上线有效」是两回事 |
| 样本 | 120 个申万二级板块 × **349 个评价日** = **41,762 行**；区间 **2019-07-16 ~ 2026-09-15**（每 5 个交易日取一个评价日） |
| 持有期 | 短期 5 日 / 中期 20 日 / 长期 60 日 / 更长期 120 日 |
| 保真度 | 用真实归档 `20260916_0745.json` 对照重建值（720 对）：**合计 Spearman 0.946**、平均绝对差 0.0489。差异来源已知 = 生产缓存最后一根 K 线是 13:40 预热时的**盘中**价 |
| ⚠️ 覆盖范围 | **只有 6 个维度可回溯**（动量 / 趋势 / 量价 / 换手 / 估值 / 周期，原始权重合计 54%）。主力资金流、出清度、政策、新闻情绪、板块共振 + 筹码罚分**需要当期快照，历史不可得** → 本节的「组合分」是**6 维内重新归一**的技术面口径，**不是**线上 12 维总分 |
| ⚠️ 为什么不用 `backtest.py` | 远端归档**全部是同一天**（2026-09-16）的多次运行，按日期去重后样本数 = **1** → 「样本不足」是**结构性**的，**不是再等 2–4 周就好**。v2.1 的 P1 待办在这点上判断错了 |

#### 6.5.1 短期 / 中期 / 长期：三个视角的组合分表现

| 视角 | 持有期 | IC 均值 | IC>0 占比 | 多空均值 | 分层单调 |
|---|---|---|---|---|---|
| **短期** | 5 日 | **-0.016** | 49.43% | 0.08% | ❌ |
| **中期** | 20 日 | **-0.031** | 46.38% | 0.06% | ❌ |
| **长期** | 60 日 | **-0.038** | 47.48% | 0.34% | ❌ |
| 更长期 | 120 日 | **+0.018** | 52.31% | 2.17% | ❌ |

**怎么读这张表**：IC 都在 0 附近、短期到中期偏负、分层**从不单调**。诚实的结论是
**「6 维技术面组合分作为横截面选板块信号，信息量接近于零，甚至轻微反向」**——
不能读成「分数越高的板块越值得买」。120 日 IC 转正且多空 2.17%（胜率 58.8%）是唯一偏正面的一格，
但样本重叠严重、且分层仍不单调，不足以支撑「长期有效」的说法。

> 分年看（`backtest_report_hist.md` §5.9）：组合分 IC **2019–2020 明显为正**（+0.06 ~ +0.31），
> **2021 起转负并持续到 2026**。也就是说「这套分曾经好用，之后失效」——
> 接手人必须知道这条时间线，不能拿早期样本的漂亮数字当现状。

#### 6.5.2 逐因子：哪条规则真在贡献信息

| 因子 | 权重 | 短期 IC | 中期 IC | 长期 IC | 更长期 IC | 分年符号一致性 | 判定 |
|---|---|---|---|---|---|---|---|
| `momentum` | 10% | -0.010 | -0.025 | -0.043 | -0.002 | 5/8 | 证据冲突（IC 负、配对为正）→ 须逐项拆 |
| `trend` | 10% | 0.001 | -0.014 | -0.026 | 0.020 | 5/8 | 近乎无信息 |
| `volume_price` | 8% | -0.026 | -0.025 | -0.040 | -0.027 | **8/8 全负** | 方向相反，**且符号稳定** |
| `turnover` | 8% | **-0.055** | **-0.076** | **-0.083** | **-0.076** | **5/5 全负** | **方向相反，且是全表信息量最大的** |
| `valuation` | 10% | 0.005 | -0.003 | 0.007 | 0.061 | 4/8 | 近乎无信息 |
| `cycle` | 8% | -0.017 | -0.029 | -0.028 | 0.018 | 5/8 | 近乎无信息 |

**逐日配对**（同日末档 − 首档，比均值可靠，因为它只在同一天内比较）：

- `trend` 拆开后发现**内部打架**：MA 排列项是**对的**（多头排列 − 破 MA20：120 日 **+0.20pt**），
  但 KDJ 的 J 值项**方向相反**——J>80 超买 反而比 J<0 超卖 好 **+1.96pt（120 日）**，
  与「超买该卖」的直觉相反。**KDJ 那两项在拖累整个 trend 因子。**
- `momentum`：近 5 日涨幅 >10% 比 <-10% 中期差 **-1.39pt**（追高短炒不行），
  但近 20 日 / 60 日 涨幅的方向是正的（+0.98 / +1.62pt，120 日）→ **「用 5 日动量」是拖累项**。
- `turnover`：换手最高 20% 比最低 20% 中期差 **-0.60pt**、长期差 **-1.09pt**（为正的日期仅 36%）。

#### 6.5.3 两处「实现 ↔ 文档」不一致的实证裁定（**处理方式完全不同，别搞反**）

| 维度 | 现行实现 | 数据裁定 | 该改哪边 |
|---|---|---|---|
| 换手率位置 | `_pctrank(turnover)` = 换手越高分越高 | 低换手明显更好（最高 20% 比最低 20% 长期差 -1.09pt） | **改代码**（方向写反了） |
| 估值位置 | 无 PE 时 `_pctrank(close)` = 价格越高分越高 | 价格最高 20% 比最低 20% 长期好 **+2.64pt** | **只改注释**（`valuation()` 的 docstring 沿用了 PE 的「越低越好」，代码方向是被数据支持的） |

**这两条是本报告最可执行的产出**：只看代码不看数据、或只看注释不看数据，都会各改错一边。
另附量化影响：把 `turnover` 反向后，组合分 IC 从 -0.016/-0.031/-0.038/+0.018 改善到
**-0.001/-0.014/-0.021/+0.036**（即**去掉了一项持续扣分的成分**）；把 `valuation` 反向则让 IC 更负
→ **不要顺手反转估值**。

#### 6.5.4 解禁罚分（`chip_supply`）：假设站不住

用东财解禁明细的**真实字段**做事件研究（**17,355 条事件**，2019-01-02 ~ 2026-09-16，每条自带解禁前/后 20 日涨跌幅）：

| 口径 | 解禁前 20 日 | 解禁后 20 日 |
|---|---|---|
| 全体 | -0.36% | **+1.84%** |
| 占比 >10%（现行重罚档） | -1.61% | **+1.79%** |
| 占比 <0.5%（现行几乎不罚） | +1.42% | +1.62% |

- 「占比越大 → 解禁后越弱」**不成立**（>10% 档的解禁后收益甚至略高于全样本）。
- 「解禁前会跌」**成立**（-1.61%，市场提前反应），但**罚分打在「未来 30 日解禁」上，方向错了**。

**⚑ 处置（2026-09-16 已落地）**：上表是「个股事件」口径。为了把结论钉死，又补了一次
**生产同款口径**检验（报告 §5.7.1）：逐评价日重建「未来 30 日成分股解禁市值 ÷ 板块总市值」，
再过**同一个** `factors.chip_supply()`，看「被罚得越狠的板块，未来超额收益是不是越差」。
四个独立口径**方向完全一致**（中期 = 20 交易日）：

| 口径 | 中期（20 日）超额差 | 为正的日期占比 |
|---|---|---|
| A 有解禁 − 无解禁 | +0.05pt | 52% |
| B 占比 ≥5%（吃满） − 无解禁 | +1.16pt | 53% |
| C 生产罚分 9–12 分 − 0 分 | **+0.82pt** | 53% |
| D 解禁/成交额 >3 天 − 无解禁（**不依赖市值回溯**，交叉验证） | +0.44pt | 51% |

→ 解禁压力越大，未来**不是更差、而是略好**。照原样罚分等于**系统性扣掉随后跑得更好的板块**。

**处置动作**：`weights.yaml` 的 **`release_weight: 12.0 → 0.0`**（解禁退出罚分）。
三条边界说清楚：

1. **不反向加分** —— 效应量很小（中期最重罚档 − 无解禁仅 +0.82pt）、且中段不单调
   （6–9 分段为负），反向属过拟合。
2. **不丢信息** —— 解禁占比与解禁市值仍逐板块写在产物
   `penalty_detail.release_ratio / release_mv_yi` 里；事件日历的「解禁高峰」照旧展示。
   **它从「扣分项」降级为「提示项」**。
3. **减持项保留**（上限 4 分）—— 减持公告历史不可得、无法回测；但「内部人卖出」的理论依据
   比解禁强，且权重很小。

> 想恢复原行为：把 `release_weight` 改回 `12.0` 即可（纯配置，不改代码）。
> 逐年不稳定（2023 与 2026 为负，2019/2020/2025 显著为正）这一点仍然成立 ——
> 所以结论的强度是「**不要当利空来罚**」，而不是「**它是利多**」。

#### 6.5.5 宏观门（M ≥ 70 进攻 / 40 ≤ M < 70 中性 / M < 40 防守）

四要素里**政策（需新闻历史）与情绪（需涨停家数历史）不可回溯**，只能用流动性 0.30 + 量价 0.25 在 0.55 内重新归一得 `M6`，故**只看排序性，绝对水平与生产口径不可比**（样本 636 天，受两融数据起点 2024-01 限制）：

| M6 分档 | 沪深300 未来 20 日 | 未来 60 日 | 胜率(60日) |
|---|---|---|---|
| 低（均值 37.4） | 1.22% | **5.03%** | **69.01%** |
| 中（均值 51.6） | 1.11% | 3.77% | 58.46% |
| 高（均值 68.6） | 0.97% | 1.64% | 48.57% |

且样本只有 2024 年以后，**结论是「存疑」而不是「推翻」**。若要动决策矩阵，先把四要素历史补齐。

## 8. 工程红线与约定（改动前务必确认）

| 约定 | 原因（都是踩过的） |
|---|---|
| **归档必须带 `demo` 字段** | `make_demo.py` 写 `true` → `backtest.load_snapshots` 自动剔除 → 进 `summary.skipped_demo` 头部显示。`main.py` 写 `false`。**新增任何写归档的代码都要带它**，否则合成数据污染 IC / 分层 / 多空胜率 |
| **归一化只做一次** | `chips.release_ratio()` 返回**原始比例**（0.025 = 2.5%），归一化只在 `factors.chip_supply()` 内。曾因双重归一化导致罚分吃满 |
| **构建失败必须保留上一版产物** | `main.py` 在无任何板块完成评分时 `SystemExit` |
| **数据源一律三级重试 + 单点失败降级** | 绝不因单个标的失败中断整体评分 |
| **无源标的不要重试** | 用 `NoHistorySource`，见 4.5 |
| **因子一律输出 [0,1] 分位分（250 日窗口）** | 避免绝对阈值随市场漂移 |
| **接口列名用候选列表匹配** (`_pick_col` / `_pick`) | 抗字段改名；匹配失败返回中性值不报错 |
| **pandas 3.x：`to_numpy()` 可能返回只读视图** | 禁止原地运算（如 `arr -= arr.mean()`），需 `np.array(..., copy=True)` |
| **权重与阈值全部外置到 `weights.yaml`** | 改配置不改代码 |
| **K 线缓存绝不入 git** | parquet 每日全量重写，约 3 MB/日 → 年约 1 GB。CI 用 `actions/cache@v4` |
| **改前端后必须升 `web/sw.js` 的 `VERSION`** | 浏览器只在 `sw.js` **字节变化**时才重装 SW。只改 `app.js` 不改 `sw.js` → 老用户永远看到旧界面且**毫无报错**。当前 `wb-v3`（v2.0 为 `wb-v2`） |
| **改 `web/` 下静态文件后必须重跑 workflow** | Pages 发布的是 CI 上传的快照，不是分支内容 |
| **事件日期不许伪装成官方公布** | 事件日历只有 `src=eastmoney` 是日历源的真实事件；`rule`/`release` 是推算，`curated` 是惯例。前端必须显式标出「规则/解禁/惯例」，新增任何事件来源都要带 `src` |
| **`events_rules.json` 的顺序就是优先级** | 命中第一条即返回，所以 `us_other` / `cn_other` 这类兜底规则必须排在各自类别的最后，否则会把该类别下所有事件都吃掉 |
| **评估信号一律用「同日超额收益」+ 点内重建**（v2.2） | 用绝对收益会把市场 beta 混进来 —— 实测同一规则两种口径会给出**相反**结论；重建时**只把 `df[:t+1]` 喂给线上原函数**，否则「回测通过」与「上线有效」是两件事 |
| **`bt_data/` 必须在 `web/` 之外**（v2.2） | Pages 发布的是 `web/` 快照，回测原料（K 线 / 解禁明细 / 面板 CSV）放进去会被**匿名访问**。已列入 `.gitignore`，但它同时是「随时可重抓的原料」，删了不影响线上 |

### 8.1 Service Worker 缓存策略（已从 cache-first 改为 SWR）

静态资源用 **stale-while-revalidate**：先返回缓存秒开，后台带 `cache:'no-cache'`
条件请求刷新（GitHub Pages 有 ETag，未变更仅 304），命中 200 才写回。
这样**下次加载自动拿到新版**，不再只依赖「记得改 VERSION」这种人工纪律。

`data/` 走**网络优先**（保证评分是当天最新的），失败回退缓存（离线可看）。

## 11. 回归测试（改前端必跑，这是唯一的防线）

浏览器里跑的逻辑 **CI 和本机都覆盖不到**，一旦产物字段改名，
页面上只会**静默地少显示一块内容**（甚至白屏），没有任何报错。故有两个 node vm 自测：

| 脚本 | 覆盖 | 断言数 |
|---|---|---|
| `tools/check_render.mjs` | 大盘关键位卡片（含**日线档**、位置区 ×N）、回撤列表行数与位置条、窗口×排序 12 种组合无 NaN、详情页因子拆解、**事件日历**（字段完整性、日期格式、高优先渲染、优先级/类别筛选、tab 徽章）、产物 schema 完整性 | **52** |
| `tools/check_live_paging.mjs` | 域名优先级、单页上限、翻页取全量、零重复、**线上真实清单命中率** | 6 |

做法：把 `web/app.js` 丢进 node vm、禁用 `boot()`、塞最小 DOM stub，
再用**线上/本地真实产物**调用渲染函数，断言输出 HTML 里确实出现关键内容。

**验收标准**：命中率必须 **100%**，且「拉回条数 == 唯一 code 数」。
`check_live_paging.mjs` 同时也是「翻页有没有真的生效」的哨兵 ——
不翻页只有 68/120，一跑就知道。

**回测侧没有自动化断言，但有一个内建的自检**：`backtest_hist.py` 每次运行都会调
`verify_against_archive()` —— 只要 `bt_data/archive/` 下有真实快照（没有就用
`--fetch-archive` 从 GitHub 拉一份，已验证可直接拉），它就会在**开头**打印
「重建 vs 归档：Spearman x.xxx」，对照基准见本文件 6.5.0 与报告 §1。改 `factors.py` 之后：

- **必须重跑** `backtest_hist.py --reuse-panel`（秒级）看因子 IC 是否按预期变化 ——
  对照基准见 6.5.2 的表；
- 若 Spearman 明显掉下来（**低于 0.90**），说明重建与线上已经不是同一套逻辑了，
  此时报告里的所有结论都作废 —— **别拿它当「因子已改好」的证据**。

### 11.2 面板指纹（`--reuse-panel` 的守卫，2026-09-16 收窄口径）

`backtest_hist.py` 会把 `factor_rev`（8 位 md5）写进 `bt_data/backtest_hist_panel.meta.json`；
带 `--reuse-panel` 复用时先比对，不符就**拒绝复用**。原因：面板里存的是**已经算好的因子值**，
拿旧公式的面板去评价新公式**不会报错**，只会得到一张看起来正常、结论却张冠李戴的报告。

**口径（2026-09-16 修正）**：

```
factor_rev = md5( PANEL_SCHEMA + {window, 6 个可回溯权重} + factors.py 全文 )[:8]
```

- **只覆盖真正进面板的东西**。最初是整个 `weights.yaml` 一起哈希，导致改一个与面板毫不相干的键
  （如 `penalty.release_weight`、`macro.weights`、`archive.summary`）也会被拒、白等 8 分钟重建。
  而 `build_panel` 只用到 `F.*` 与 `S.combine(f, w6)` → 真正相关的只有 `window`
  （`_pctrank` 的滚动窗口）与 `BACKTESTABLE` 那 6 个权重。
- **`PANEL_SCHEMA`**（当前 `2`）：当 `build_panel` 的**取值逻辑**变了（列的算法、预筛条件、
  `LOOKBACK`）而 `factors.py` 没动时，**手工 +1**，旧面板同样会被判过期。
- 报告头部会打印本次指纹。**跨指纹的结论不要直接对比数值**。

> 应急开关 `--allow-stale-panel`：明确表示「我知道这面板的因子可能已变」才用，
> 用于「已确认改动不进面板」的场景（例如只改了解禁罚分）。用之前先想清楚为什么安全。

| 3 | SW 纯缓存优先 + `sw.js` 未变 | 改动推上去了但老用户永远看到旧界面 | **改前端必升 `VERSION`**；已改 SWR 作第二道保险 |

| 12 | **归档快照全是同一天** | `backtest.py` 恒报「样本不足」，看起来像「再攒几周就好」；实际 11 份归档按日期去重后 **只剩 1 天** | **判断「样本会不会自己长出来」要看内容维度（日期），不是文件个数** |
| 13 | **回测用绝对收益而不是同日超额** | 同一规则的两种口径给出**相反**结论 —— 低换手行业一度显得特别好，其实只是「低换手」扎堆在市场底部 | **横截面回测一律先减当日全市场等权收益**；再加一层「逐日配对（末档 − 首档）」抗档位成分漂移 |

| 15 | **取数接口的隐藏上限** | 腾讯 K 线 `count ≥ 2050` 返回**空数组**（HTTP 200、不报错）；东财解禁明细单季**恰好 400 行**封顶 | **「返回 200 但条数刚好是个整数」通常就是上限**，二分探出来写进注释；解禁要逐月分片绕开 |
| 16 | **重型计算算完才渲染，改一个字要重跑 8 分钟** | `extreme_spread` 对非分类列返回 `{}`，下游 `or (x or {}).get(...)` 落在 list 上 → 崩在**报告渲染阶段**，前面的面板重建全部作废 | **①函数契约写清「只接受 Categorical」②面板算完立刻落盘（CSV + meta），渲染从盘上读** |
| 17 | **「证据表」跟随当前配置 → 自毁** | §5.7.1 的解禁同款口径检验原来读 `weights.yaml` 的 `release_weight`。按它的结论把该值改成 0 之后，**它自己算出来的罚分全变成 0**：报告里出现「被罚占比 0.0%」「最重罚档 − 无解禁：—」，整张证据表塌成一档 —— 而脚本**不报错** | **论证「该不该改某个配置」的检验，口径必须锚在「改动前」，不能读当前配置**；阈值/上限这类没变的参数可以读。现在固定用常量 `RELEASE_W_ORIGINAL = 12.0` 并在报告里显式声明 |
| 18 | **同一份报告里同一个词指两个持有期** | §6.2 的列名硬编码写「中期」，但代码取的是 `H[len(H)//2]` —— 4 档下是**第 3 档 = 60 日（长期 1 季）**，而第 2 / 6.1 节里「中期」指的是 **20 日**。同一份报告、同一个词、两个含义；引用的 +1.55pt 是 60 日、控制台打的 +0.82pt 是 20 日，**两个数都对，但列名会让人对错号** | **持有期标签一律从 `HN` 映射取，不手写**；用 `H[len(H)//2]` 时把实际档位名和数字一起打出来。控制台输出同样要标数字 |
